# Plan 01-01 — Core domain + config resolver vertical slice

## Objective

实现 `ai-dev-manager` 的第一个可测试闭环：定义最小领域模型，并把四层配置解析成 `EffectiveConfig`，支持继承、覆盖、禁用和来源追踪。

完成后项目仍然没有 UI、MCP 网络服务或 Shell；但后续所有能力都有稳定配置语义可依赖。

## Scope Guard

本 Plan **只做**：

- Go module
- model
- config resolver
- unit tests
- 最小文档同步

明确不做：

- 配置文件 IO
- MCP 连接/启动
- Skill 文件扫描
- Runtime execution
- Shell / Git / Docker
- Wails / Desktop UI
- CodexPro / DevSpace adapter

发现上述需求时只记录到 `.planning/`，不要顺手实现。

## Task 1 — Bootstrap Go module and minimal package layout

**Create:**
- `go.mod`
- `internal/model/config.go`
- `internal/config/resolver.go`

**Requirements:**
- module 名使用稳定、暂不依赖 GitHub 仓库地址的本地模块名策略；若 Go module 必须选择路径，可先用 `ai-dev-manager`，发布前再迁移。
- 不添加第三方 dependency，除非标准库明确无法满足当前 Phase。
- 不创建 runtime/mcp/docker/git 等空 package。

**Verify:**
- `go test ./...` 至少能够发现 package；如果当前 MCP shell 无 Go，则记录环境 gap，不以猜测代替验证。

## Task 2 — Implement minimal domain types

**Implement in:** `internal/model/config.go`

最低需要：

- `Scope`
- `Workspace`
- `MCPDefinition`
- `SkillDefinition`
- `Policy`
- `ConfigLayer`
- `EffectiveConfig`
- resolved/source trace 所需的最小类型

**Rules:**
- `Enabled` 采用三态语义。
- map/slice 必须复制，resolver 不得通过共享引用 mutate 输入。
- env map 必须 deep-copy 至少一层。
- runtime state（PID、port、process）不进入这些配置类型。

**Verify with tests:**
- bool pointer 三态辅助函数或 fixture 可读。
- clone 后修改输出不会反向修改输入。

## Task 3 — Implement deterministic resolver

**Implement in:** `internal/config/resolver.go`

建议 API：

```go
func Resolve(layers ...model.ConfigLayer) (model.EffectiveConfig, error)
```

如果为了强制层序更安全，可以改成明确参数：

```go
func Resolve(global model.ConfigLayer, profile, project, runtime *model.ConfigLayer) (model.EffectiveConfig, error)
```

优先选择能最清晰表达固定层序、减少调用方传错顺序的 API。

**Merge rules:**
1. Global 必须是 global scope。
2. 其余层 nil 可跳过。
3. scope 与参数位置不匹配时返回错误。
4. MCP/Skill 按 ID merge。
5. 高层只覆盖其明确给出的值。
6. `Enabled=false` 保留实体但最终 disabled。
7. 更高层 `Enabled=true` 可重新启用。
8. Policy 采用最后一个非空定义。
9. 记录最终来源；至少记录实体主来源和 Enabled 来源。
10. 所有结果按稳定顺序导出或使用 map + deterministic helper，避免测试依赖随机 map iteration。

## Task 4 — Build table-driven test matrix

**Create:** `internal/config/resolver_test.go`

至少测试：

1. global-only。
2. profile policy override。
3. project adds private MCP。
4. project disables global MCP。
5. runtime re-enables MCP。
6. project overrides global Skill path。
7. runtime disables Skill。
8. nil optional layers。
9. invalid scope placement。
10. empty MCP ID / Skill ID。
11. input layers are not mutated。
12. env map is copied, not aliased。
13. source trace is correct。
14. deterministic repeated resolve gives equal result。

测试命名要描述业务语义，不要只写 `TestResolve1/2`。

## Task 5 — Review architecture against Phase 1 exit criteria

检查：

- Core 是否完全不知道 Wails。
- Core 是否完全不知道 MCP SDK / transport。
- Runtime 是否尚未出现具体实现。
- `EffectiveConfig` 是否足以让后续 Phase 2/3 消费，而不是暴露 resolver 内部状态。
- 是否为了“未来可能需要”引入了无测试支撑的抽象；有则删除或回退。

## Task 6 — Verification and GSD transition

运行：

```text
go test ./...
```

若可用，再运行：

```text
go vet ./...
```

完成后：

1. 更新 `.planning/STATE.md`。
2. 在 `.planning/PROJECT.md` 将 CONF-01..07、RUN-01、COMPAT-01 中真正验证完成的条目移到 Validated；不要因为“模型存在”就错误标记 WORK-01 完成。
3. 记录实现过程中产生的新决策。
4. 如果全部 Exit Criteria 通过，将 Phase 1 标记完成并为 Phase 2 创建 Context/Plan。
5. 如果 Go 工具链仍不可用，Phase 状态保持 verification blocked，而不是宣称完成。

## Definition of Done

Plan 01-01 完成必须同时满足：

- 代码实现完成。
- table-driven tests 覆盖 merge/disable/trace/immutability。
- `go test ./...` 有真实通过结果。
- 没有跨 Phase 功能混入。
- `.planning/` 与实际实现同步。
