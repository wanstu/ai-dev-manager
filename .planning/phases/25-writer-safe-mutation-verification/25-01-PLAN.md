# Phase 25 Plan 25-01 — Writer-guarded Mutation, Execution, and Verification

## Objective

Complete v0.6 by routing write/edit/exec/verifier operations through the stable Gateway MCP with mandatory writer ownership, managed-worktree revalidation, and a concurrency boundary that prevents release/destroy from invalidating an in-flight mutation.

## Requirements Covered

- GW-05
- final v0.6 acceptance for GW-01..08

## Implementation Steps

### 1. Upgrade Environment coordination lock

Change Manager `mu` from `sync.Mutex` to `sync.RWMutex` without changing existing writer/destroy semantics.

- AcquireWriter/ReleaseWriter/Destroy keep `Lock`.
- mutation Invoke uses `RLock` across its full critical section.
- existing read-only `InvokeRead` remains unlocked so independent reads are not unnecessarily blocked.

Run existing Phase 20/21 writer/destroy tests after the change.

### 2. Add `InvokeMutation`

Protocol-neutral Environment Manager method:

```text
InvokeMutation(ctx, environmentID, writerOwner, operation, input)
```

Flow under `RLock`:

1. validate id/owner/operation allowlist.
2. Store.Get current Environment.
3. require active writer and exact owner match.
4. call existing `validatedRuntimes`.
5. concrete capability check.
6. Invoke derived Runtime.
7. only on successful Runtime Invoke, reload/update the local Environment lease timestamp, UpdatedAt and LastActivityAt, then Store.Put.
8. return Runtime result.

Allowed operations/capabilities:

- files.write -> files.write
- files.edit -> files.edit
- shell.exec -> shell.exec
- verify.run -> verify.run
- verify.run_many -> verify.run

Wrong/missing owner => `ErrWriterNotOwner`; do not automatically acquire/renew a different owner.

### 3. Concurrency tests

Use blocking fake Runtime:

- acquire owner A;
- start InvokeMutation and block inside Runtime Invoke;
- concurrently ReleaseWriter and Destroy;
- assert both remain blocked until Runtime is released;
- after successful invoke, writer/activity renewal is persisted before release/destroy proceeds.

Also prove two mutations can enter concurrently under `RLock` (representing separate Environments) instead of being globally serialized.

Run `go test -race ./internal/environment`.

### 4. Extend Gateway core + MCP adapter

Gateway Service forwards `InvokeEnvironmentMutation` to Manager.

Add tools with required `environment_id` + `writer_owner`:

- write: path/content/create_parents
- edit: path/old_text/new_text/expected_replacements
- exec: executable/args/cwd/timeout_ms/max_output_bytes
- run_verifier: id
- run_verifiers: ids

Use common structured output `{ok,result,error}` and Phase 23 domain error behavior.

No shell string and no raw worktree operations.

### 5. Adapter and validation tests

- Gateway total surface = 19 tools.
- missing writer_owner => structured invalid_input before Runtime.
- wrong owner => structured writer_not_owner.
- correct owner forwards exact operation/input.
- runtime/domain errors remain tool errors with stable structured code.
- verifier structured failure result remains `ok=true` when Runtime call itself succeeded.

### 6. Real MCP multi-Environment acceptance

With one Workspace and two Environments:

1. acquire writer A and B through Gateway.
2. write/edit A and B through Gateway with different contents.
3. read back through Phase 24 tools; prove isolation and main checkout unchanged.
4. run git_status/git_diff per Environment; prove independent changes.
5. wrong writer cross-call is rejected.
6. daemon restart preserves endpoint and writer leases.
7. correct writers continue mutation after restart.

### 7. Exec + verify acceptance

Use a project config with safe allowed executables/verifier.

- exec safe structured command succeeds under correct writer.
- disallowed executable remains Runtime policy error through Gateway.
- run_verifier/run_verifiers return real structured verifier results.
- verifier fail result is returned as successful tool result when verifier execution itself completed.

### 8. Final regression and milestone gate

Normal development/full gate must be unattended and must not open real TCP listeners. Network-bearing tests use `ADM_NETWORK_ACCEPTANCE=1` as an explicit opt-in; ordinary `go test ./...` skips them while core/manager/in-memory MCP coverage remains active.

Targeted/race/full unattended gate:

```text
go fmt ./...
go test ./...
go test -race ./internal/environment ./internal/gateway ./internal/adapter/mcpgateway ./internal/daemon
go vet ./...
go build -o ai-dev-manager-v0.6-review.exe ./cmd/ai-dev-manager
```

Real daemon / Runtime MCP / Gateway Streamable HTTP acceptance is separate:

```powershell
.\scripts\network-acceptance.ps1 -Go D:\tools\go\go1.26.5\bin\go.exe
```

The script uses two stable executable paths: `.test-bin\ai-dev-manager-network-daemon.exe` for the real daemon and `.test-bin\ai-dev-manager-network-tests.exe` for each network-bearing test package compiled via `go test -c`. `cmd/ai-dev-manager` test `TestMain` injects the fixed daemon path through the existing `daemon.Start(..., executable)` parameter; production daemon start logic does not read or depend on the acceptance environment variables.

After unattended gate + explicit network acceptance pass:

- GW-05 -> Validated.
- README documents final Gateway development tool surface, writer flow, and unattended/network test split.
- mark Phase 25 complete and v0.6 complete.
- stop at milestone boundary for review/commit/tag; do not auto-start v0.7.

## Stop Conditions

Stop rather than weaken safety if:

- writer validation cannot remain atomic with Runtime mutation versus release/destroy;
- supporting exec would require raw shell strings;
- verifier behavior would require converting ordinary verifier fail into infrastructure/domain error;
- Direct MCP compatibility would require breaking changes.

## Exit Decision

v0.6 completes only when two external-Agent task Environments can be independently read and mutated through one stable Gateway MCP URL, with writer ownership and Runtime security enforced by ADM rather than prompt convention.
