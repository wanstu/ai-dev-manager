# 21-02 — Agent/Admin verifier lifecycle surface and long-operation acceptance

Requirements: 21-01 requirements plus ADM-GW-001/003 and Phase-20 context guidance continuity.
New prerequisites: none.
Execute only after 21-01 acceptance and summary are committed.

## Objective

Expose the owner-local verifier-run lifecycle through the shared Agent/Admin MCP surface, make the existing blocking verifier path diagnose request interruption clearly, update compact Environment guidance for long verification, and close Phase 21 with real client-disconnect/restart evidence.

- do not start Phase 22 automatically.

## Task 1 — Shared Agent/Admin async verifier tools

Likely files: `internal/gateway/server.go`, Gateway focused tests, 21-01 owner lifecycle files only if integration exposes a defect.

Register the same tools on Agent and Admin surfaces:

- `environment_verifier_run_start`
- `environment_verifier_run_list`
- `environment_verifier_run_status`
- `environment_verifier_run_cancel`

Inputs:

- start: `environment_id`, `writer_owner`, `verifier_id`, optional `max_output_bytes`;
- list: `environment_id`;
- status: `environment_id`, `verifier_run_id`;
- cancel: `environment_id`, `writer_owner`, `verifier_run_id`.

Surface contract:

- start description says this is the preferred path for long/heavy verifier/test/build work and returns immediately with stable owner-local identity;
- list/status are read-only and never acquire/renew a writer;
- cancel requires writer authority and never accepts raw PID;
- output includes lifecycle state, verifier identity, bounded live stdout/stderr + truncation flags, timestamps, structured error evidence and terminal `verifier.Result` when present;
- Agent/Admin behavior is equivalent for these tools;
- `environment_verifier_list` continues to mean verifier definitions;
- existing `environment_verifier_run` remains a blocking compatibility tool.

## Task 2 — Clear blocking-path diagnostic and context guidance

Likely files: `internal/app/service.go` or shared verifier helper, `internal/gateway/server.go`, `internal/app/environment_context.go`, focused tests.

Improve the synchronous path without inventing an arbitrary duration threshold:

1. Successful blocking verifier calls retain current result semantics.
2. Verifier-defined timeout remains a classified `verifier.Result` with `timed_out=true`; it is not converted to a transport/tool error.
3. If the caller/request context is canceled or its outer deadline interrupts the blocking call before verifier classification, return a stable diagnostic such as `blocking_request_interrupted` with a concise message directing long verification to `environment_verifier_run_start`.
4. Do not automatically start an async verifier after interruption, continue work secretly, or retry the command.
5. Update `environment_verifier_run` description to state that it is blocking and async lifecycle is preferred for long operations.
6. Update Phase-20 `environment_context_bundle` verifier guidance to mention async start/status/cancel for long verification. Bundle generation must remain passive and must not enumerate/start verifier runs unless owner-observed counts are explicitly added as a bounded fact in this plan.

If owner `gateway_info` gains an `owned_verifier_runs` count, it must be observational only and count currently running verifier runs; do not persist it or make it a prerequisite. Adding this count is optional and should be done only if it materially improves acceptance/debugging without widening scope.

## Task 3 — Integrated G01–G12 acceptance

### G01 — Plain optionality

A non-Git Environment with no verifier remains fully usable for files/context. Async verifier start fails locally only because the requested verifier is absent; no verifier becomes a global prerequisite.

### G02 — Stable owner lifecycle across clients

Through real Streamable HTTP, client A starts a long verifier and disconnects. Client B on the same Gateway owner lists/statuses the same `vfrun_`, sees early bounded output, and observes terminal success/failure.

### G03 — Cancellation authority

Wrong writer cannot cancel. Matching launch writer can cancel, reaches terminal `canceled`, and the owned process tree stops. Status after cancel remains queryable while the owner lives.

### G04 — Verifier semantics preserved

Pass/non-zero/timeout retain `verifier.Result` semantics exactly enough to preserve existing sync meaning: verifier ID/kind, status, exit code, duration, timeout flag, summary and bounded output.

### G05 — Output bounds

Large live stdout/stderr remains bounded at the requested/default budget and reports truncation explicitly during running and terminal states.

### G06 — Start validation has no ghost resources

Missing/disabled verifier, wrong writer, forbidden executable, escaped cwd and managed-root validation failure produce no installed verifier-run identity.

### G07 — Sync diagnostic

A blocking request interrupted by its caller context returns the new stable long-operation diagnostic when a response is still possible; verifier-defined timeout remains a normal failed verifier result. Successful short sync verifier regression remains green.

### G08 — Owner/Environment cleanup and restart

Environment drop and Gateway owner shutdown cancel active verifier runs. After Gateway restart, verifier-run list is empty, old `vfrun_` IDs are invalid, and `state.json` contains no verifier-run observations/results.

### G09 — Existing generic Run/process boundaries

`run_start/list/status/cancel`, process lifecycle/logs and their owner counts/cleanup remain green. Phase 21 does not alias verifier resources into `run_` or `proc_`.

### G10 — Context/capability/privacy boundaries

Context guidance advertises async verifier usage for long work but remains read-only. Memory values, Skill content, MCP probing and Git execution are not introduced by verifier inspection/status.
