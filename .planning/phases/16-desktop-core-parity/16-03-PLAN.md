# 16-03 Plan — Management Plane, Admin MCP and Desktop Connection Profiles

## Why this exists

Phase 16-02 made MCP/Skill Desktop management usable, but it also exposes a boundary ambiguity in the current Desktop architecture:

- Desktop constructs `app.New(statePath)` locally and reads/writes the persisted ADM state directly.
- The HTTP Gateway is a separate runtime process and is optional for Desktop CRUD.
- The current Store mutex is process-local, not a cross-process file lock.
- The current HTTP Gateway is loopback-only and rejects remote listen/Host values.
- The current `/mcp` surface mixes host-level administrative tools with Agent development tools.

This means Desktop can appear to manage ADM while ADM Gateway is stopped, and separate Desktop/Gateway/CLI processes may operate on the same persisted state without one canonical management owner. That is acceptable as an early local implementation, but it is not the desired long-term management architecture.

## Decision

Use one canonical **Admin / Management MCP** contract for normal management clients.

### Normal clients

- Desktop is an Admin MCP client.
- CLI management commands are Admin MCP clients.
- Remote management uses the same Admin MCP contract.

### Separate Agent and Admin surfaces

- Agent MCP remains the development-capability surface for an external coding Agent.
- Admin MCP is the privileged host-management surface for Desktop/CLI/operator workflows.
- Administrative operations must not be automatically exposed to an ordinary Agent connection merely because they exist in Core.

Candidate endpoint split:

- `/mcp` — Agent MCP.
- `/admin/mcp` or `/management/mcp` — Admin MCP.
- `/healthz` — service identity/liveness/version.

The exact path name may be finalized during implementation; the semantic separation is required.

## Connection profiles

Desktop should support an explicit ADM connection profile instead of assuming `127.0.0.1:43137`.

Profile fields:

- display name;
- scheme (`http` / `https`);
- host/domain;
- port;
- optional base path;
- derived health URL;
- derived Admin MCP URL;
- whether the profile is local or remote;
- authentication reference when remote admin authentication is implemented.

Default profile:

- `http://127.0.0.1:43137`

Desktop should show a clear connection state before rendering management data:

- connected;
- stopped/unreachable;
- incompatible ADM version;
- unauthorized;
- TLS/network error.

## Local bootstrap behavior

Local Desktop should remain easy to use.

Preferred local flow:

1. Desktop checks configured `/healthz`.
2. If local ADM is stopped, Desktop may offer/start the local ADM process.
3. Once healthy, Desktop connects through Admin MCP.
4. Desktop management data comes from Admin MCP, not direct file reads.

Starting/stopping a local process is a local bootstrap capability, not a remote management action.

## Direct state-file access

Direct state-file access should **not** remain an equal normal runtime mode.

Reason:

- it bypasses the live runtime owner;
- it cannot provide owner-local MCP/process/run observations;
- it creates possible cross-process write races because current Store locking is process-local;
- it cannot represent a remote ADM instance;
- it risks Desktop/CLI behavior diverging from Admin MCP semantics.

Keep direct-file access only as an explicit **offline/bootstrap/recovery** path.

Recommended rules:

- normal Desktop/CLI management: Admin MCP only;
- offline state inspection: explicit command/mode, preferably read-only;
- offline mutation, if ever supported, requires explicit safety design such as service-stopped verification and cross-process locking;
- no transparent fallback from failed Admin MCP to writable direct-file mode.

This prevents a disconnected Desktop from silently editing a local state file while the user thinks it is managing a remote ADM.

## CLI role

Do not create a separate CLI management protocol.

CLI is a client surface over the same Admin MCP contract.

Exceptions that may remain local/bootstrap commands:

- start local ADM service;
- stop/restart local ADM service with owner-safe checks;
- inspect local installation/config path;
- explicit offline recovery/doctor operations.

This gives Desktop and CLI the same authoritative management semantics.

## Admin MCP privilege boundary

Candidate Admin-only operations include:

- Workspace register/rename/remove;
- Environment create/rename/remove;
- executable allowlist mutation;
- global MCP definition add/update/import/remove/default policy;
- Skill source add/refresh/remove/default policy;
- global Memory mutation;
- local service configuration;
- future temporary resource cleanup policy;
- future connection/auth configuration.

Candidate Agent-facing operations remain Environment-scoped capabilities such as:

- Environment inspection/capability report;
- bounded files/search/read/write/edit/delete under Environment authorization;
- allowed exec/verifier/process/run lifecycle;
- selected MCP tool inventory/call;
- selected Skill availability/read;
- optional Git/worktree operations where authorized.

Exact tool migration must be compatibility-planned rather than removed blindly.

## Remote management security

Remote Admin MCP must not be enabled by simply accepting arbitrary Host headers.

Before non-loopback remote admin is considered safe, implementation must define:

- authentication;
- authorization/scope for Admin MCP;
- TLS or trusted reverse-proxy boundary;
- origin/Host handling;
- secret/reference storage for Desktop connection credentials;
- no literal credential leakage in snapshots/logs/UI.

Until that exists, default local loopback behavior remains the safe supported configuration.

## Implementation slices

### 16-03A — Management contract split ✅

- Classify existing Gateway tools as Agent, Admin or shared.
- Build a separate Admin MCP server/surface using existing Core services.
- Preserve existing Agent capabilities required for coding workflows.
- Add tests proving Admin-only tools are absent from ordinary Agent MCP.

### 16-03B — Desktop connection profile + health ✅

- Replace hard-coded default Gateway status calls with a configurable base URL/profile.
- Health check configured domain/host/port.
- Show connection state before management data.
- Local start/stop controls only when profile points to an eligible local ADM instance.

### 16-03C — Desktop management through Admin MCP ✅

- Replace direct `app.New(statePath)` management calls with an Admin MCP client.
- Keep local process bootstrap separate from management transport.
- Ensure disconnected/remote states never silently fall back to writable local state.

### 16-03D — CLI convergence ✅

- Move normal CLI management commands to the same Admin MCP client abstraction.
- Retain only explicit bootstrap/offline commands as direct-local exceptions.

### 16-03E — Remote enablement, only after auth design ⏸️ post-RC by default

- non-loopback/HTTPS profiles;
- authentication/reference handling;
- remote-admin negative tests.

Remote enablement may be deferred beyond local 1.0 RC if authentication is not yet ready.

## RC positioning

Schedule 16-03 after 16-02 manual UI dogfood, but before final 1.0 RC declaration for the **local management-plane convergence** pieces.

RC target:

- 16-03A Agent/Admin surface split;
- 16-03B configurable local Desktop connection profile + health;
- 16-03C Desktop normal management through local Admin MCP.

16-03D CLI convergence is strongly preferred before RC because CLI direct writes have the same cross-process consistency concern; if it is deferred, RC notes must make the limitation explicit and concurrent CLI/Desktop mutation must not be advertised as safe.

16-03E true non-loopback remote enablement may be deferred beyond the first local RC until authentication/TLS semantics are ready.

Direct-file management should not become the permanent architecture and must not be an invisible fallback.

## Validation

- Agent MCP tool inventory excludes Admin-only tools after split.
- Admin MCP exposes required Desktop/CLI management operations.
- configurable health check distinguishes stopped/incompatible/healthy endpoints.
- local Desktop can bootstrap local ADM then manage it through Admin MCP.
- remote profile never causes local state fallback.
- normal Desktop/CLI management no longer requires direct writable state-file access after 16-03C/D.
