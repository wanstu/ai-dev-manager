# 16-01 Plan — Desktop Parity Inventory, GitHub CI Baseline and RC Gate

## Goal

Reframe Phase 16 as the immediate 1.0 RC path. Build a precise Desktop Core parity inventory, add a GitHub Actions CI/build baseline, and define the minimum local 1.0 RC gate before broader UI work.

## Motivation

The remaining Phase 14/15/17 items improve ADM's usefulness and polish, but the base Core functionality is already present after Phases 10-13. A Desktop management surface plus automated CI build is now the most important missing product capability for daily use and a local 1.0 RC.

## Scope

16-01 is RC infrastructure and inventory first.

Inventory areas:

1. Workspace and Environment lifecycle.
2. Environment capability report and structured reasons.
3. MCP catalog, import, selection, health/status, inventory and diagnostics.
4. Skill sources, refresh, selection, availability and support-file read diagnostics.
5. Runtime files/tree/read/search/write/edit/delete with writer safety.
6. Exec allowlist and command execution status.
7. Verifier list/run/results.
8. Process lifecycle/logs/ports.
9. Generic run lifecycle.
10. Optional Git status/diff/branch and managed worktree isolation.
11. Memory visibility: counts and keys where appropriate, never private values by default.
12. Error, degraded capability and unavailable-capability display.
13. Local smoke/doctor workflow for RC.

CI baseline:

1. Add `.github/workflows/ci.yml`.
2. Trigger on `push` to `master`, `pull_request`, and manual `workflow_dispatch`.
3. Use repository read-only permissions.
4. Set up Go from `go.mod`.
5. Run Windows full `go test -count=1 ./...` and `go vet ./...`.
6. Build Windows CLI artifact.
7. Build Windows Desktop smoke binary artifact.
8. Build CLI artifacts on Windows/Linux/macOS.
9. Upload short-retention artifacts for RC smoke review.

## Non-goals

- No installer/tray/autostart/updater/signing work.
- No release tag or GitHub Release publishing yet.
- No temporary resource cleanup implementation unless inventory proves it blocks RC.
- No GitNexus/provider implementation unless inventory proves it blocks RC.
- No Planner/Executor/Reviewer or `.planning` execution semantics.
- No Desktop-only state or authorization model.

## Deliverables

1. `.github/workflows/ci.yml` GitHub Actions workflow for test/vet/build/artifacts.
2. `16-RC-GATE.md` defining local 1.0 RC criteria, smoke checklist, CI requirements and known limitations policy.
3. `16-PARITY-MATRIX.md` mapping Core capability -> application service/API -> existing Desktop exposure -> gap -> RC priority.
4. Planning updates marking Phase 16 as current priority and Phase 14/15/17 as non-blocking unless proven otherwise.

## Acceptance Criteria

1. CI workflow is present and intentionally conservative: no deploy, no push, no release publishing, no secret use.
2. CI validates Windows full test/vet/build and produces artifacts for CLI plus a Windows Desktop smoke binary.
3. The parity matrix identifies every Core capability relevant to daily use.
4. Every Desktop gap is classified as RC-blocking, post-RC, or not applicable.
5. RC criteria are explicit and testable.
6. The plan preserves Core boundary and safety rules.
7. Active development remains on `master`; no push unless explicitly requested.

## Validation

Planning/CI baseline gate:

- Local smoke build of CLI and Desktop Windows binaries must pass.
- `git diff --check` must pass.
- No functional app code changes are required for CI baseline.
- ROADMAP and STATE must reflect RC-first priority honestly.

Implementation slices after inventory must also run:

- focused Desktop tests for changed UI/adapter behavior;
- relevant app/gateway/management tests if service boundaries change;
- `go test -count=1 ./...`;
- `go vet ./...`;
- `git diff --check`.
