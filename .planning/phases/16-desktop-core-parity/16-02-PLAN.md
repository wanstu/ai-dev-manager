# 16-02 Plan — Desktop MCP and Skill Visual Management UI

## Goal

Make MCP and Skill management in Desktop genuinely usable for a local 1.0 RC.

This is the first product-facing Phase 16 implementation slice because MCP and Skill are the core ADM capabilities that most need a human-friendly configuration and diagnostic surface. CapabilityReport rendering, verifier/process/run visibility and other Desktop gaps remain important, but MCP/Skill visual management is the first RC user journey.

## User-facing outcome

A user should be able to open Desktop and answer these questions without using the CLI:

1. Which MCPs and Skills are configured?
2. Which ones are enabled by default for new Environments?
3. Which ones are enabled for a selected Environment?
4. Which ones are usable, degraded, unavailable, disabled or unconfigured?
5. Why is a specific MCP/Skill not usable?
6. What safe action can I take next: add/import, enable/disable, refresh, probe, inspect, remove?

## UX principles

### Separate definition from Environment selection

Desktop must clearly distinguish:

- global MCP/Skill definition or source;
- default inclusion for future Environments;
- current Environment selection;
- observed health/availability for one Environment.

A common UX bug would be making a user think that removing an MCP from one Environment deletes the global definition, or that default inclusion changes existing Environments. The UI must avoid that.

### Show state before actions

Each MCP/Skill row/card should show the current state badge before exposing actions:

- available / healthy;
- degraded;
- unavailable / error;
- disabled;
- unconfigured;
- unresolved.

Actions should be contextual and safe. Destructive actions require confirmation and must say whether they remove a global definition/source or only change one Environment selection.

### Prefer guided flows over raw JSON

Desktop can preserve CLI/Gateway power-user flows, but RC users need guided flows:

- Add MCP with transport-specific fields.
- Import MCP JSON/JSONC with preview before apply.
- Add Skill source with root/support roots.
- Refresh Skill source and inspect refresh result.
- Enable/disable for one Environment from a clear Environment picker.

### Evidence over guesswork

Error and status panels must use Core diagnostics:

- MCP desired config validation and runtime health/status where available;
- Skill source refresh result and Environment availability diagnostics;
- CapabilityReport facts for the selected Environment;
- never private Memory values or resolved secret values.

## Information architecture

### Top-level Desktop layout

Keep the current dashboard, but make MCP and Skill first-class sections rather than small catalog lists.

Recommended navigation:

1. Overview
2. Environments
3. MCPs
4. Skills
5. Runtime
6. Memory
7. Settings / Diagnostics

For 16-02, implementing separate visual MCP and Skill sections is enough; full navigation polish can be incremental if the same journeys are usable.

### MCP management screen

Primary zones:

- Summary strip: total MCPs, enabled defaults, selected Environment enabled count, unhealthy/unconfigured count.
- Toolbar: Add MCP, Import config, Refresh/Probe selected, filter by state, filter by transport.
- MCP list/table/cards:
  - name/id;
  - transport: streamable-http or stdio;
  - endpoint configured or executable configured, without leaking secrets;
  - default include toggle;
  - selected Environment enabled toggle;
  - health/status badge;
  - last observed/check time when available;
  - action menu: inspect, probe, edit if supported, remove.
- Detail panel:
  - desired config summary;
  - Environment selection status;
  - health/status diagnostics;
  - CapabilityReport facts for `mcp/<id>`;
  - import/source provenance when known;
  - safe remove confirmation copy.

### MCP add/import flows

Add MCP form:

- name;
- transport selector;
- streamable-http fields: endpoint, optional header reference keys, health policy basics;
- stdio fields: executable, args, env reference keys;
- default include checkbox;
- validation errors from Core; no silent best-effort persistence.

Import flow:

- paste/upload JSON/JSONC content or choose known format input supported by existing Core surfaces;
- preview candidates, warnings, errors and reference requirements;
- apply only after explicit confirmation;
- show created/updated definitions and unresolved reference requirements after apply.

16-02 may implement import as a guided paste textarea first; file picker/native import can follow if needed.

### Skill management screen

Primary zones:

- Summary strip: total sources, discovered Skills, selected Environment enabled count, unavailable/broken count.
- Toolbar: Add Skill source, Refresh selected/all, filter by availability, filter by source.
- Source list:
  - source id/root;
  - support roots count;
  - default include setting;
  - last refresh result/time;
  - discovered artifact count;
  - actions: refresh, inspect result, remove source.
- Skill list/table/cards:
  - skill name/id;
  - source/artifact path;
  - selected Environment enabled toggle;
  - availability badge;
  - reason/message for disabled/unconfigured/unavailable;
  - support file count when available;
  - actions: inspect, list support files, read safe diagnostic file if already supported.
- Detail panel:
  - availability state/reason;
  - source/artifact/support roots;
  - support inventory summary;
  - CapabilityReport facts for `skill/<id>`;
  - refresh errors without breaking unrelated Skills.

### Environment detail integration

Environment detail should include MCP and Skill tabs or sections:

- selected MCPs and Skills for that Environment;
- toggles for enabling/disabling catalog entries;
- health/availability badges;
- reason messages;
- links/actions to open the global MCP/Skill detail.

The same Core selection APIs remain authoritative; Desktop must not create Desktop-only selection state.

## Implementation scope

### P0 for 16-02

- Adapter methods for missing MCP import preview/apply and typed MCP config where Management already has surfaces.
- Adapter methods for Skill source list/refresh/remove and Skill availability where Management already has surfaces.
- Frontend MCP screen with add/import/list/default/Environment enable/health/detail basics.
- Frontend Skill screen with source add/list/refresh/remove, Skill list, Environment enable, availability/detail basics.
- Clear state badges and diagnostics for disabled/unconfigured/unavailable/degraded/available.
- Secret/private Memory safety tests.
- Desktop adapter tests and frontend smoke-friendly structure.

### P1 follow-up if needed for RC

- More polished filters/search/sorting.
- Bulk enable/disable for selected Environment.
- Health probe batch action with clear progress.
- Skill support file browsing/read, bounded and explicitly user-triggered.
- MCP edit flow beyond add/import if Core update semantics are already stable.

### Post-RC

- Full GitNexus/provider UI.
- Temporary resource cleanup UI.
- Full process/run/verifier dashboards.
- Full file manager/editor.
- Installer/tray/autostart/updater/signing.

## Non-goals

- Do not add Desktop-only persistence or authorization.
- Do not execute MCP tools from Desktop as part of management UI.
- Do not resolve or display secret values.
- Do not display private Memory values in snapshots or normal diagnostic panels.
- Do not implement installer/release publishing.
- Do not resume Phase 14 GitNexus work or Phase 15 cleanup implementation in this slice.

## Validation

Focused tests:

- Desktop adapter exposes MCP import/config/source/availability operations through Management without bypassing Core.
- MCP/Skill UI data mappers preserve definition/default/Environment-selection separation.
- Rendering functions show state/reason and avoid secret/private Memory values.
- Remove/disable actions are distinguishable in labels/copy.

Full gates:

- `go test -count=1 ./cmd/ai-dev-manager-desktop ./internal/desktop ./internal/management`
- `go test -count=1 ./...`
- `go vet ./...`
- `git diff --check`
- CLI and Desktop smoke build continue to pass.

## Done when

A user can use Desktop, without CLI fallback, to configure/import MCPs, configure/refresh Skill sources, enable/disable MCPs and Skills for an Environment, and understand core health/availability reasons well enough for local RC dogfood.
