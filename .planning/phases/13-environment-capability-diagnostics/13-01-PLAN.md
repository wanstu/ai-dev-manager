# Plan 13-01 — Resilient Capability Fact Model + Static Environment Report

## Objective

Replace all-or-nothing capability inspection with one reusable structured fact model and application-level report that continues across optional component failures.

## User-visible outcome

Even when Git, a Skill, an MCP or a managed worktree is broken, Environment inspection still explains which capabilities are available/unavailable instead of returning one opaque top-level error.

## Tasks

### 1. Define one shared CapabilityFact schema

Create application-level types for:

- capability key/kind;
- state (`available`, `disabled`, `unconfigured`, `unavailable`, `degraded`);
- stable reason code;
- sanitized message;
- `requires_writer`;
- evidence with explicit ADM identity/config facts;
- observation/source timestamp fields where applicable.

This schema is later reused by Gateway/CLI/Desktop; do not create transport-specific variants.

### 2. Refactor Environment inspection into independent evaluators

Build component evaluators for at least:

- file read/tree/search;
- file mutation/write/edit/delete;
- exec;
- verifier definitions;
- Git;
- managed isolation/root validity;
- selected/unresolved MCP desired state;
- selected/unresolved Skill desired state.

Convert component failures into facts. Top-level failure is reserved for inability to resolve the Environment/ADM store itself.

### 3. Reuse real validators

Where availability depends on Runtime/allowlist/path/isolation validation, call the same validator/service boundary used by the real operation or extract a shared validator. Do not duplicate a weaker diagnostic-only check.

Capability inspection does not run commands/verifiers or mutate state.

### 4. Model writer requirement honestly

Writer-gated facts expose:

- `requires_writer=true`;
- current lease status/owner/expiry as already-visible Environment facts;
- no claim that the caller owns the lease unless caller identity is explicitly supplied by a later API contract.

Inspection never acquires/renews/releases writer.

### 5. Static failure-isolation acceptance

Prove non-Git, invalid verifier config, unresolved MCP/Skill selection and invalid/tampered root cases return useful fact sets rather than all-or-nothing failure.

Plant Memory/secret sentinels and prove static report never includes them.

## Done when

ADM has one structured, side-effect-free application-level capability report model whose facts agree with real validators and whose optional failures are local.
