# Plan 10-01 — Persistent Local Daemon + Cross-process Control

## Objective

交付 v0.3 的第一个 vertical slice：真实 `ai-dev-manager start/status/stop` 可以跨独立 CLI process 控制同一个长期 daemon；daemon 长期持有一个 `controlplane.Service`，但暂不接管 Phase 11 的 Workspace Runtime/MCP start/status/stop。

## Task 1 — Daemon domain + discovery metadata

Create a focused package (name按实现最小化，优先 `internal/daemon`) that owns:

- daemon instance metadata: instance ID, PID, loopback control endpoint, started time/version if useful。
- config-root-scoped runtime metadata path。
- atomic metadata write/read/remove。
- stale metadata detection/cleanup hooks。
- typed status/errors for not-running/already-running/stale/corrupt metadata where useful。

Constraints:

- no persisted Runtime/ClientSession/listener objects。
- no generic process manager abstraction。
- no database。

Verification:

- metadata round trip。
- corrupt/stale metadata handling。
- one config root has one discoverable owner semantics。

## Task 2 — Local daemon server

Implement a minimal loopback-only control server using Go standard library where practical.

Surface required for Phase 10:

```text
GET /health
POST /stop
```

Daemon runtime:

- construct exactly one `controlplane.Service` for the config root。
- bind local control listener only。
- publish discovery metadata only after listener/control plane are ready。
- graceful stop calls `Service.StopAll` before process exit。
- cleanup metadata only when it still belongs to the current instance, avoiding deletion of a newer daemon's metadata。

Verification:

- non-loopback listen rejected。
- health returns same instance identity as metadata。
- stop triggers graceful daemon exit and Control Plane cleanup。

## Task 3 — CLI start/status/stop thin client

Modify `cmd/ai-dev-manager` without duplicating daemon/control-plane business logic.

Implement:

```text
ai-dev-manager [--config-root ...] start
ai-dev-manager [--config-root ...] status
ai-dev-manager [--config-root ...] stop
```

`start`:

- if a healthy daemon is already discoverable, return its status/idempotent result rather than creating another owner。
- otherwise launch the same executable in a hidden/internal daemon mode as a detached/background child suitable for current Windows acceptance and portable fallback where possible。
- wait only for deterministic readiness/failed-start result needed to return correct CLI status; no arbitrary sleep-based success claim。

`status`:

- discover metadata, probe the control API, and report observed health rather than trusting a PID file alone。

`stop`:

- issue control stop to the discovered healthy daemon and confirm it is no longer healthy / metadata is cleaned within bounded lifecycle logic。

Machine-readable `--json` output remains supported.

## Task 4 — Process-level acceptance

Add tests that prove the lifecycle across separate processes, not only multiple objects in one test process.

Required acceptance shape:

```text
process A: ai-dev-manager --config-root <temp> start
process A exits

process B: ai-dev-manager --config-root <temp> --json status
→ running, same daemon instance/PID

process C: ai-dev-manager --config-root <temp> stop
→ daemon exits

process D: status
→ not running
```

Also verify repeat `start` does not create a second healthy owner.


Then review the diff and run a real Windows binary lifecycle acceptance where tool execution permits.

- no persistent Workspace runtime desired-state implementation yet。

- no generic dev-server/process manager。
- no Docker/Debug/DAP。
