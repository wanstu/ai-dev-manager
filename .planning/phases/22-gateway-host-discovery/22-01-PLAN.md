# Phase 22 Plan 22-01 — Persistent Gateway Host and Discovery MCP

## Objective

实现一个 daemon-owned、restart-stable、loopback-only 的 Gateway MCP endpoint，并通过真实 MCP client 暴露 `gateway_info/workspace_list/environment_list/environment_inspect` 四个 discovery tools；不修改 Direct MCP contract。

## Requirements Covered

- GW-01
- GW-02
- GW-08 foundation
- GW-06 discovery-error foundation

## Implementation Steps

### 1. Add protocol-neutral Gateway discovery service

Create a small core service/interface boundary consumed by MCP adapter:

- WorkspaceLister
- EnvironmentLister
- EnvironmentInspector
- GatewayService with methods for info/list/inspect

Keep it free of HTTP/MCP SDK types.

`gateway_info` should identify the product as AI Coding Environment and describe the current discovery surface without embedding secrets or speculative Agent logic.

Tests:

- workspace list is stable and sorted/uses registry truth.
- environment list does not mutate LastActivityAt.
- inspect delegates to Environment Manager rather than reading Store directly.

### 2. Add `internal/adapter/mcpgateway`

Create an MCP server separate from `mcpserver.New(runtime)`.

Tools in Phase 22 only:

- `gateway_info`
- `workspace_list`
- `environment_list`
- `environment_inspect`

Use typed SDK schemas.

For Environment domain failures, preserve stable error code in the tool error text, e.g.:

```text
environment_not_found: environment "env_x" not found
```

Do not expose raw wrapped/internal error chains.

Add loopback Streamable HTTP handler. Reuse narrow Host/Origin protection helpers only if that does not alter Direct MCP behavior; otherwise keep Gateway helper local.

Adapter tests with fake discovery service verify tool list/schema and calls.

### 3. Add persistent Gateway desired store

Create daemon-level persisted state separate from desired runtimes, for example `gateway.json` under the daemon config root:

- version
- desired_running
- listen (concrete address after first successful dynamic bind)

Atomic save/version/error behavior should follow existing desired store patterns.

Rules:

- old/missing file => disabled Gateway.
- never persist `127.0.0.1:0` after a successful first start; persist the actual bound address.
- explicit listen must be loopback.

Tests cover reload/version/malformed/desired transitions.

### 4. Add daemon GatewayOwner

GatewayOwner owns observed listener/server and desired state.

Operations:

- `Up(ctx, requestedListen)`
- `Status()`
- `Down(ctx)`
- `Reconcile(ctx)` on daemon startup
- `CloseObserved(ctx)` on daemon stop while preserving desired state

Status fields:

- desired_running
- state: stopped/running/error
- listen
- endpoint
- error

Startup semantics:

- no persisted listen + no requested listen => bind `127.0.0.1:0`, then persist actual address after success.
- persisted concrete listen => bind exactly it.
- requested explicit listen conflicting with existing desired concrete listen while already configured => return conflict rather than silently moving.
- bind failure on reconcile => keep desired_running=true + same listen and expose error status; do not choose another port.

Use the same Environment Manager instance already created by daemon Run so Gateway inspect sees the same persisted Environment truth.

### 5. Add daemon Control API

Register loopback control endpoints:

- `POST /gateway/up`
- `GET /gateway/status`
- `POST /gateway/down`

Control client helpers mirror existing runtime/environment patterns.

Daemon startup calls GatewayOwner.Reconcile after Environment Manager is constructed.
Daemon shutdown closes observed Gateway server without clearing desired state.

### 6. Add CLI

Top-level:

```text
ai-dev-manager gateway up [--listen ADDR]
ai-dev-manager gateway status
ai-dev-manager gateway down
```

- `up` ensures daemon running.
- human output prints state/endpoint.
- `--json` returns structured GatewayStatus.
- `status` can report stopped/desired/error clearly.
- `down` only affects Gateway, not Workspace runtimes or Environments.

Update top-level usage string.

### 7. Real MCP + restart acceptance

Process-level test with isolated config root and real Git Workspace/Environment:

1. register workspace and create one Environment.
2. `gateway up` without explicit port.
3. assert returned listen is concrete non-zero loopback and endpoint ends `/mcp`.
4. connect with official MCP Streamable HTTP client.
5. call `gateway_info`, `workspace_list`, `environment_list`, `environment_inspect`.
6. record Environment LastActivityAt; discovery inspect may compute facts but must not touch activity.
7. stop/start daemon.
8. `gateway status` returns same endpoint.
9. reconnect MCP client to same URL and discovery still works.
10. verify Direct MCP server test remains unchanged/passing.

Port-conflict test:

- stop daemon preserving desired Gateway.
- occupy persisted gateway listen with a test listener.
- start daemon.
- Gateway status reports desired=true/error for same listen; no new random endpoint.

## Stop Conditions

Stop rather than weaken the product contract if:

- stable endpoint would require silently changing persisted port on restart.
- Gateway implementation would require pretending it is a Workspace Runtime.
- discovery would need to bypass Environment Manager managed-worktree validation.
- non-loopback exposure would require disabling Host/Origin/auth protections.
- Direct MCP tool surface would need a breaking change.

## Exit Decision

Phase 22 is complete only when one Gateway MCP URL remains stable across daemon restart and real MCP clients can discover Workspace/Environment state through it. No lifecycle mutation or routed file/git tools in this phase.
