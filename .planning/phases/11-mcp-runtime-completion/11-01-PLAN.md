# Plan 11-01 — Typed MCP Configuration + HTTP/Stdio Transport Runtime

## Objective

Replace the generic MCP catalog shape with one explicit MCP desired-config model and make both supported transports (`streamable-http`, `stdio`) real under the existing Gateway owner.

## User-visible outcome

A user can configure either a remote/local Streamable HTTP MCP or a local stdio MCP once, enable it for an Environment, and ADM can activate it without confusing Skill fields, leaking secrets, or opening a second arbitrary-process authority path.

## Tasks

### 1. Introduce a typed MCP definition

Primary areas:

- `internal/model/types.go`
- `internal/catalog/`
- application/management/CLI/Gateway MCP inputs that currently consume generic `CatalogEntry`

Define a dedicated persisted MCP type with:

- stable ID/name/default-include;
- `transport` = `streamable-http` or `stdio`;
- explicit supported auth mode (`none` / secret-backed headers for HTTP);
- HTTP endpoint/header refs;
- stdio executable/args/env refs;
- explicit `health_policy` with configurable check interval, probe timeout, auto-reconnect flag and reconnect interval; `auto_reconnect` defaults to `false`, and reconnect policy is fixed-interval only in Phase 11.

Transport-specific validation must reject mixed/irrelevant fields. Do not preserve legacy compatibility fields merely because the state is pre-stable.

Keep Skill persistence behavior unchanged in this plan except for whatever type separation is mechanically required.

### 2. Generalize activation without exposing resolved secrets

Refactor app-owned MCP activation into a transport-specific resolved activation type.

- Streamable HTTP resolves endpoint/header refs only at activation.
- Stdio resolves configured env refs only at activation.
- Missing refs produce structured activation/config errors.
- Returned status/inspection structures contain only reference/config facts, never resolved values.

Do not add OAuth token persistence. Unsupported auth must fail clearly.

### 3. Add stdio/command transport under the persistent owner

Use the official Go MCP SDK command/stdio transport rather than implementing JSON-RPC framing manually.

For stdio activation:

- executable must be currently allowlisted by ADM;
- process cwd is the selected Environment root;
- process is owned by the existing Gateway runtime owner;
- disable/removal/Environment drop/Gateway close terminates it through transport/session close;
- no arbitrary PID API is exposed.

Streamable HTTP continues using the current SDK transport and secret-backed headers.

### 4. Keep Gateway/management surfaces explicit

Update MCP add/inspect/list inputs/outputs so transport-specific configuration is understandable without exposing secrets.

Do not add Agent task semantics. These APIs configure/use runtime capability only.

### 5. Real transport acceptance

Add real acceptance for:

- Streamable HTTP tool list/call after model refactor;
- stdio helper MCP tool list/call;
- stdio executable rejected when not allowlisted;
- child process cleanup on disable/owner close;
- missing secret reference and unsupported transport/auth are local failures;
- unrelated file/Skill operations remain green.

## Done when

- both advertised transports are implemented, not metadata-only;
- stdio cannot bypass executable authority;
- desired config and runtime observation remain separated;
- secret values never persist/return through normal inspection;
- existing Streamable HTTP behavior remains real and green.
