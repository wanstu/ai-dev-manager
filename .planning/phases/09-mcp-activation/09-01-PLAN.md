# Plan 09-01 — Configured MCP Activation & Health

## Objective

完成 v0.2 最后一个 vertical slice：从 Workspace EffectiveConfig 读取 explicitly-enabled MCP Definition，使用官方 MCP Go SDK 建立 stdio / Streamable HTTP client session，完成真实健康探测并通过 Control Plane / CLI 暴露安全状态。

## Task 2 — MCP activation manager

Create:

```text
internal/mcp/activation.go
internal/mcp/activation_test.go
```

Implement:

- health states: `unprobed`, `disabled`, `starting`, `healthy`, `error`, `stopped`。
- session key = Workspace ID + MCP ID。
- stdio transport: `exec.CommandContext`/`exec.Command` with executable + Args; no shell parsing。
- streamable HTTP transport: official SDK StreamableClientTransport。
- EnvRefs resolve only at activation boundary using injected lookup; missing ref returns structured error with ref name only。
- child environment uses minimal safe host variables + explicit Env + resolved EnvRefs rather than inheriting the entire process environment。
- Connect + ListTools establishes healthy; store sorted tool names and retain session until Stop。
- duplicate activation should replace/reject deterministically; prefer idempotently returning current healthy status if same key already active。
- Stop and StopWorkspace close retained sessions and update/remove runtime state safely。

Verification:

- real stdio MCP fixture using current test executable helper mode。
- HTTP health probe using existing MCP HTTP host fixture。
- missing EnvRef structured error and no value leakage。
- Workspace A/B same MCP ID produce independent active sessions。

## Task 3 — Control Plane and CLI surface

Modify:

```text
internal/controlplane/service.go
internal/controlplane/service_test.go
cmd/ai-dev-manager/main.go
cmd/ai-dev-manager/main_test.go
```

Control Plane:

- `ActivateConfiguredMCPs(workspaceID, runtimeOverride)` resolves EffectiveConfig and activates only explicitly enabled entries。
- `MCPStatuses(workspaceID, runtimeOverride)` returns configured + runtime health view, including disabled/unprobed entries without starting them。
- `StopConfiguredMCP(workspaceID, mcpID)` / `StopConfiguredMCPs(workspaceID)`。
- Service owns one activation manager so lifecycle is process-local and isolated.

CLI:

```text
ai-dev-manager ... mcp activate --workspace <id>
ai-dev-manager ... mcp status --workspace <id>
ai-dev-manager ... mcp stop --workspace <id> [--id <mcp-id>]
```

Because v0.2 has no daemon, CLI activation/status across separate process invocations is not persistent; commands are still useful for in-process tests and future embedding, while normal `serve` can activate configured MCPs in-process before exposing the workspace endpoint if needed by the final acceptance flow.
