# Phase 23 Plan 23-01 — Agent-facing Environment Lifecycle and Structured Domain Errors

## Objective

Extend the stable Gateway MCP from discovery-only to safe Environment lifecycle without exposing worktree internals: create/destroy/writer acquire/release all delegate to v0.5 Environment Manager and return structured, recoverable domain errors.

## Requirements Covered

- GW-03
- GW-06
- GW-07

## Implementation Steps

### 1. Extend protocol-neutral Gateway Service lifecycle contract

Extend EnvironmentSource/Manager dependency with:

- `Create(ctx, environment.CreateRequest)`
- `Destroy(ctx, envID, force)`
- `AcquireWriter(ctx, envID, owner)`
- `ReleaseWriter(envID, owner, force)`

Add Gateway Service forwarding methods. Do not duplicate lifecycle policy.

Add protocol-neutral `DomainError`:

- code
- message
- environment_id
- facts/warnings/hints

Add helpers that sanitize `*environment.Error` without exposing wrapped/internal error chains.

For unsafe destroy / writer conflict, best-effort attach useful facts:

- if Environment snapshot has writer, attach writer facts.
- if inspect succeeds after failure, reuse inspect facts/warnings/hints.

Tests prove error codes and no prescriptive fields.

### 2. Add lifecycle typed MCP schemas

`environment_create` input mirrors `environment.CreateRequest`.

`environment_destroy`:

- environment_id
- force

writer acquire/release as Context defines.

Outputs use explicit structs:

- `ok`
- successful result (`inspection` or `environment`)
- optional structured `error`

On domain failure return:

- `CallToolResult{IsError:true}`
- typed output with `ok=false` + DomainError
- nil Go error when this preserves typed structured output

Add adapter test proving SDK emits both `isError=true` and structured error content. If SDK does not preserve structured output this way, use manual Server.AddTool for lifecycle tools while keeping explicit input/output JSON schemas; do not fall back to error strings only.

### 3. Preserve Environment Manager policy

Gateway tools only call Gateway Service/Environment Manager:

- create does not use raw Git worktree ops.
- destroy does not delete branch.
- force only when input explicitly true.
- writer conflict does not auto-force/steal.

No `git_worktree_*` tool registration in mcpgateway.

### 4. Update Gateway info/tool list

`gateway_info.tools` and capabilities reflect lifecycle additions.

Tool list at end Phase 23 exactly:

```text
environment_create
environment_destroy
environment_inspect
environment_list
environment_writer_acquire
environment_writer_release
gateway_info
workspace_list
```

### 5. In-memory lifecycle MCP tests

Use fake Gateway Service/Environment Manager to verify:

- create arguments map correctly.
- destroy force remains explicit.
- writer arguments map correctly.
- structured branch_exists/writer_conflict/unsafe_destroy output.
- tool error is visible to MCP client without protocol-level failure.
- raw worktree tools absent.

### 6. Real process-level Gateway lifecycle acceptance

With isolated config root + real Git Workspace:

1. `gateway up` once.
2. MCP `environment_create` -> ready Environment.
3. MCP list/inspect sees it.
4. MCP writer acquire owner A succeeds.
5. daemon restart; same Gateway endpoint + writer A persists.
6. owner B acquire -> structured writer_conflict.
7. normal destroy while writer active -> structured unsafe_destroy.
8. writer release owner A.
9. make Environment dirty through direct test filesystem mutation (routed write belongs Phase 25).
10. normal destroy -> structured unsafe_destroy with dirty fact.
11. force destroy through MCP -> succeeds; verify branch remains.
12. create duplicate requested branch -> structured branch_exists.

Also one MCP create with `include_changes=true` from dirty base proves the flag reaches existing Manager path.

## Stop Conditions

Stop rather than weaken boundaries if:

- typed MCP lifecycle errors cannot preserve stable error codes without leaking internals; adapt MCP registration instead.
- Gateway lifecycle would require raw worktree exposure.
- force behavior would become implicit/automatic.
- writer conflict handling would require stealing another owner.

## Exit Decision

Phase 23 completes only when a real external MCP client can manage Environment lifecycle through the one stable Gateway URL while v0.5 safety semantics remain intact.
