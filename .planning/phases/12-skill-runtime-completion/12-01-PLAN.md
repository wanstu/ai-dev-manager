# Plan 12-01 — Skill Sources, Stable Identity + Atomic Refresh

## Objective

Replace name-only discovered Skill identity with explicit persisted Skill sources and authoritative per-source refresh while preserving Environment selection as the authorization boundary.

## User-visible outcome

Users can register Skill sources once, refresh them explicitly, safely discover additions/removals, and distinguish same-name Skills from different sources without silent rebinding.

## Tasks

### 1. Add persisted SkillSource management

Introduce a source model containing:

- stable source ID;
- canonical discovery root;
- configured support roots;
- default-include policy;
- source metadata required for management/inspection.

Expose thin management/Gateway/CLI operations for source list/add/remove/refresh. Registering a source must never scan outside that explicit root.

### 2. Make SkillDefinition source-aware

Separate the discovered Skill artifact definition from source configuration.

Stable Skill identity must derive from source ID plus source-relative artifact path, not display name. Two sources may expose Skills with the same name.

Content changes at the same source-relative artifact path preserve ID.

### 3. Implement atomic per-source refresh

Refresh one source by discovering the full current source snapshot, then atomically replacing only that source's discovered Skill definitions.

Return added/updated/removed counts and resulting source status.

Critical failure rule:

- discovery/source failure leaves the previous source-owned catalog snapshot intact;
- only a successful source scan may confirm removals.

### 4. Preserve explicit unresolved selections

When a successfully refreshed source removes a Skill:

- remove the current discovered definition;
- do not rewrite Environment `EnabledSkillIDs`;
- old selection becomes unresolved;
- never substitute another same-name Skill automatically.

### 5. Management/state refactor

Update application/catalog/management/CLI/Gateway code to use the source-aware Skill model cleanly. Do not add pre-stable compatibility fields unless required by currently validated behavior; development state may be reset.

### 6. Acceptance

Prove:

- same-name Skills from two sources coexist;
- refresh add/update/remove semantics;
- failed refresh preserves last known snapshot;
- deleted enabled Skill becomes unresolved;
- global default/include behavior for newly created Environments remains explicit;
- unrelated MCP/file operations remain green.

## Done when

Skill catalog identity and lifecycle are based on explicit source/artifact provenance, refresh is authoritative and safe, and no name-based silent replacement remains possible.
